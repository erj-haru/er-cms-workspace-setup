# Est Rouge CMS 初回導入（/setup-workspace）

編集者（エンジニアではない人）が、Est Rouge CMS をパソコンに取り込む（Clone する）ところまでを手伝う Skill です。
環境の確認・ソフトの追加・GitHub の認証・Clone は補助スクリプト `scripts/setup.sh` が行います。
あなたの役割は、スクリプトの実行と、編集者への分かりやすい説明・承認の取り付けです。

**基本方針: 編集者にターミナルを開かせない。コマンドをコピーさせない。**
コマンドはあなたが実行し、編集者は「内容の確認・承認」「macOS が出す確認画面の操作（管理者パスワード・Touch ID・インストールの同意）」「ブラウザでの GitHub ログイン」だけを行う。
ターミナルでの手動操作は、技術的に避けられない場合（下の各所で「手動」と書いた場合）の最終手段とする。

- やり取りはすべて日本語。専門用語は避け、使う場合はひとことで言い換える（例: 「Clone（CMS 一式をパソコンに取り込むこと）」）。
- 詳しい案内文やトラブル対応は `references/setup-guide.md` にある。必要になったら読む。

## スクリプトの場所と実行方法

スクリプトは、この SKILL.md と同じフォルダの `scripts/setup.sh` です。必ず `bash` で実行します（ZIP 展開時に実行権限が失われても動くようにするため）。

```
bash "${CLAUDE_SKILL_DIR}/scripts/setup.sh" <サブコマンド> [引数]
```

`${CLAUDE_SKILL_DIR}` が置き換えられていない場合は、この Skill のベースディレクトリ（SKILL.md があるフォルダ）の絶対パスを使う。
カレントディレクトリや別リポジトリのスクリプトに頼らないこと。

| サブコマンド | 内容 | 変更の有無 |
|---|---|---|
| `check` | macOS・CPU・開発者ツール・Git・Homebrew・gh・ログイン状態・アカウント・リポジトリ権限・既存の Clone を確認 | なし |
| `install-clt` | Apple の開発者ツール（Git を含む）を macOS 標準の方法で追加し、完了を待つ | **承認後のみ** |
| `install-brew` | Homebrew 公式インストーラーを取得・署名確認し、macOS のインストーラーで開いて完了を待つ | **承認後のみ** |
| `install-gh` | Homebrew で GitHub CLI（gh）を追加し、動作を確認 | **承認後のみ** |
| `wait clt` / `wait brew` | インストールの完了を待つだけ（途中からの再開用） | なし |
| `path-status` | Homebrew が今後のターミナルでも使えるか確認 | なし |
| `persist-path` | シェルの設定ファイルに Homebrew の設定を 1 回だけ追記 | **承認後のみ** |
| `accounts` | この Mac でログイン済みの GitHub アカウントの一覧 | なし |
| `switch <アカウント>` | ログイン済みの別アカウントに切り替え、権限を再確認 | **承認後のみ** |
| `login` | ブラウザでの GitHub ログインを開始し、完了を待って権限を再確認 | **承認後のみ** |
| `suggest` | おすすめの保存先を表示 | なし |
| `plan <保存先>` | 保存先が使えるか確認 | なし |
| `clone <保存先>` | Clone（正しい Clone が既にあれば再利用） | 新しいフォルダの作成のみ |
| `verify <保存先>` | Clone 済みフォルダの確認 | なし |

出力の最後の `KEY=value` 行（特に `RESULT=` と `NEXT=`）で結果を判定する。終了コード: `0` 成功 / `1` 利用者の対応が必要 / `2` 失敗 / `3` 保存先が使えない / `64` 使い方の誤り。
**終了コードが 0 以外のときは、決して「完了しました」と伝えない。**
インストール・ログインを待つ処理（`install-*` / `wait` / `login` / `clone`）は、Bash のタイムアウトを 600000ms にする。

## 手順（会話の流れ）

### 1. 環境を自動チェックする

最初に「Mac の準備状況を確認します（何も変更しません）」と伝えて `check` を実行する。

- `RESULT=UNSUPPORTED_OS` → Mac 以外は未対応であることを伝えて終了。
- `RESULT=NEED_INSTALL` → 手順 2 へ。
- `RESULT=READY` / `NEED_LOGIN` / `NO_REPO_ACCESS` → ソフトはそろっている。手順 5 へ。
- `RESULT=NETWORK_ERROR` → インターネット接続を確認してもらい、`check` をやり直す。
- `EXISTING_CLONE=` がある → 既に CMS が取り込まれている場所。手順 7 でその場所を第一候補として示す。

### 2. 不足しているソフトをまとめて提示する

`INSTALL_PLAN`（追加する順番）をもとに、足りないものを **一度にまとめて** 説明する（`references/setup-guide.md`「不足しているソフトの説明」の文例を使う）。
各項目について、何のためのものか・編集者に何をしてもらうか（確認画面の操作など）・かかる時間の目安を書く。

- `clt` … Apple の開発者ツール（Git を含む）。macOS の確認画面で「インストール」と「同意」を押してもらう。
- `brew` … Homebrew（Mac にソフトを追加する道具）。macOS のインストーラー画面で進め、Mac のパスワード（または Touch ID）を入力してもらう。
  - `BREW_AUTO_INSTALL=no`（Intel Mac）の場合は自動で入れられない。手順 4 の「手動の場合」を参照。
- `gh` … GitHub CLI（GitHub とやり取りする道具）。画面操作は不要。

`MANAGED=yes`（学校・会社の管理下）や `IS_ADMIN=no`（管理者ではない）の場合は、「管理者の許可が必要になる場合があり、その場合は途中で止まる」ことを先に伝える。管理制限を回避する方法を試さない。

### 3. インストールの承認を得る

**まとめて一括承認にしない。** 影響範囲が違うため、各ソフトの直前に個別に承認を得る（承認の文例は `references/setup-guide.md`）。

- 承認が得られなかったソフトは入れない。「今はやめておく」と言われたら、そこで止め、「準備ができたら、もう一度 /setup-workspace を実行すれば続きから再開できます」と伝える。
- Homebrew は Mac 全体に関わる追加（`/opt/homebrew` への配置、管理者の確認）なので、特に丁寧に説明する。

### 4. Claude が必要なコマンドを実行する

`INSTALL_PLAN` の順に、承認を得たものを 1 つずつ実行する。各ステップの後に結果を伝え、次のステップの承認に進む。

1. **`install-clt`**（開発者ツール）
   - 実行前に「画面にインストールの確認が出ます。『インストール』を押し、利用許諾に『同意する』を選んでください」と伝える。
   - `CLT_READY` → 次へ。`INSTALL_WAITING` → 画面の状況をたずねる。まだ進行中なら `wait clt` で待つ。確認画面が見当たらない・エラーが出た場合は「トラブル対応」を参照。
   - `CLT_FAILED` → 理由を伝える。管理ポリシーで禁止されている可能性があれば、管理者への相談を勧めて止まる。
2. **`install-brew`**（Homebrew）
   - 実行前に「公式の配布元からインストーラーをダウンロードし、Homebrew 公式の署名と Apple の確認を受けたものか確かめてから、macOS のインストーラーを開きます。インストーラーで『続ける』『インストール』を押し、求められたら Mac のパスワード（または Touch ID）を入力してください。パスワードはこのチャットには入力しないでください」と伝える。
   - `BREW_READY` → 次へ。`BREW_PATH_PERSISTED=no` なら手順 4-4 も行う。
   - `INSTALL_WAITING` → インストーラーの状況をたずねる。進行中なら `wait brew`。閉じてしまった・キャンセルした場合は、改めて承認を得て `install-brew` をやり直す（署名確認からやり直す）。
   - `NEED_CLT` → 先に 4-1。`NO_ADMIN` → 管理者の協力が必要と伝えて止まる。
   - `BREW_DOWNLOAD_FAILED` / `BREW_VERIFY_FAILED` → 何も実行していないことを伝える。接続を確認して再試行を提案する（検証失敗が続く場合は担当者へ）。
   - `BREW_AUTO_UNSUPPORTED`（Intel Mac）→ **手動の場合**: `references/setup-guide.md`「Intel Mac で Homebrew を入れる（手動）」を案内する。終わったら `check` をやり直す。
3. **`install-gh`**（GitHub CLI）
   - `GH_READY` → 次へ。`NETWORK_ERROR` / `BREW_BUSY` → 少し待って再試行を提案（再試行も承認を得てから）。`BREW_PERMISSION` / `GH_INSTALL_FAILED` → 理由を伝え、再試行または担当者への相談。
4. **Homebrew の PATH 設定**（`BREW_PATH_PERSISTED=no` の場合だけ）
   - スクリプトは Homebrew を自動で見つけるので、この Skill の処理には不要。ただし CMS の他の Skill やターミナルで `gh` を使うために、設定が必要な場合がある。
   - `path-status` で必要性を確認し、`BREW_PATH_PERSISTED=no` なら「(PROFILE_FILE) の末尾に Homebrew の設定を 1 行追加します。既存の内容は変更しません」と説明し、承認を得てから `persist-path` を実行する。不要なら何もしない。

すべて終わったら `check` を実行し直し、`NEED_INSTALL` が消えたことを確認する。
**途中で止まった場合も `check` を実行すれば、`NEXT=` に続きのステップが表示される。** インストール済みのものは入れ直さない。

### 5. GitHub アカウントを確認する

`check` の結果に応じて進める。

- `READY` → 「GitHub のアカウント『(ACCOUNT)』を使います。CMS 用のアカウントで合っていますか？」と確認する。合っていれば手順 7 へ。違う場合は 6 へ。
- `NEED_LOGIN` / `NO_REPO_ACCESS` → 理由を伝えて手順 6 へ。

### 6. 必要なら本人による認証を開始する

アカウントの確認・切り替え・ログイン開始は、この画面（Code タブ）の中であなたがスクリプトで行う。

1. `accounts` を実行し、この Mac でログイン済みのアカウントを確認する（変更なし）。
   - `RESULT=AUTH_UNSUPPORTED`（古い gh）→ 「手動での対応」へ。
2. 編集者にどのアカウントを使うか選んでもらう（選択肢を示せる場合は選択式でたずねる）:
   - `KNOWN_ACCOUNTS` の各アカウント（使用中のものはそう示す）
   - 「別のアカウントで新しくログインする」
   - 使用中のアカウントが選ばれたら何も変更しない（`NO_REPO_ACCESS` なら、そのアカウントでは続けられないことを伝える）。
3. **ログイン済みの別アカウントに切り替える場合**
   1. 実行前に承認を得る: 「使用する GitHub アカウントを『(現在)』から『(選んだもの)』に切り替えます。『(現在)』のログインは残ったままで、いつでも戻せます。切り替えてよろしいですか？」
   2. 明確な了承を得たら `switch <選んだアカウント>` を実行する。了承がなければ実行しない。
4. **新しいアカウントでログインする場合**
   1. 実行前に、流れを説明して承認を得る（`references/setup-guide.md`「画面内でのログイン」の案内文を使う）。要点:
      - ブラウザで GitHub の確認ページが自動で開く（開かなければ https://github.com/login/device を開いてもらう）
      - 確認用のコードは自動でクリップボードにコピーされる（画面には表示しない）。ページの入力欄に `command` + `V` で貼り付ける
      - ブラウザで、CMS 用のアカウントでログインしていることを確認し、「Authorize」で承認する
      - 最大 9 分待つ。この間、こちらの画面は待機状態になる
      - 既存のアカウントのログインは残る
   2. 明確な了承を得たら `login` を実行する。了承がなければ実行しない。
5. **切り替え・ログイン後の結果**（スクリプトが使用中のアカウントとリポジトリへのアクセスを再確認している）
   - `RESULT=READY` → 「アカウント『(ACCOUNT)』で CMS にアクセスできることを確認しました」と伝え、手順 7（保存先が決まっていれば手順 8）を再開する。
   - `RESULT=NO_REPO_ACCESS` → そのアカウントには CMS を見る権限がないことを伝える。別のアカウントを選ぶか、管理者への招待依頼を案内する。
   - `LOGIN_DENIED` / `LOGIN_EXPIRED` / `LOGIN_TIMEOUT` → 理由を伝え、「もう一度ログインを始めますか？」とたずねる。再試行も改めて了承を得てから。
   - `ACCOUNT_NOT_FOUND` / `ACCOUNT_NEEDS_LOGIN` → 新しくログインし直す必要があると伝え、6-4 を提案する。
   - `SWITCH_FAILED` / `LOGIN_FAILED` / `NETWORK_ERROR` → 理由を伝え、再試行（了承を得てから）か「手動での対応」を案内する。
   - `LOGIN_UNSUPPORTED` / `AUTH_UNSUPPORTED` → この画面からは安全に操作できないため、「手動での対応」へ。
   - どの場合も、`RESULT=READY` が出るまでは「ログインできました」「切り替えました」と伝えない。
6. **手動での対応（自動でできない場合のみ）**: `references/setup-guide.md`「手動でのログイン・切り替え」を案内する。編集者が終わったと言ったら `check` をやり直す。

### 7. 保存先を確認する

1. 「CMS をどこに保存しますか？」とたずねる。`EXISTING_CLONE=` があればその場所を、なければ `suggest` の結果（ホームフォルダ内の `EstRouge/est-rouge-cms-demo`）を提案する。
   保存先の候補をあなたが勝手に作らない。固定のユーザー名やパス（例: `/Users/xxx`）を推測で書かない。
2. ユーザーの答えを `plan` に渡す（`~/…` の形でもフルパスでもよい）。
   - 指定した場所の最後のフォルダ名が `est-rouge-cms-demo` でなければ、その中に `est-rouge-cms-demo` フォルダが作られる（出力の `DEST=` が最終的な保存先）。
3. `plan` の結果:
   - `STATE=absent` / `empty` → 手順 8 へ。
   - `STATE=reuse` → 「既に正しく取り込まれているので、そのまま使います」と伝えて手順 8 へ（clone を実行しても再利用されるだけ）。
   - `RESULT=DEST_CONFLICT`（`other-repo` / `plain-dir` / `not-directory` / `broken-repo` / `incomplete-repo`）→ そのフォルダには触らないことを伝え、別の保存先をたずねて 2 からやり直す。
   - `RESULT=INVALID_DEST` → 理由を伝え、ホームフォルダ内の別の場所をたずねる。

### 8. Clone する

1. 実行前に、次の 2 点をユーザーに提示して了承を得る:
   - 取り込むもの: `https://github.com/erj-haru/est-rouge-cms-demo.git`
   - 保存先: `plan` の `DEST=` の値
2. 了承後に `clone <保存先>` を実行する。
3. 結果:
   - `RESULT=CLONED` または `RESULT=REUSED`（終了コード 0）→ 手順 9 へ。`LOCAL_CHANGES` が 1 以上なら、「保存されていない変更がありますが、消さずに残しています」と添える。
   - `RESULT=CLONE_FAILED` → スクリプトが示した「原因」「対処」を、そのまま分かりやすく伝える。
   - `RESULT=VERIFY_FAILED` → 取り込んだ内容に問題があったことを伝え、フォルダは削除していないこと、担当者に相談することを案内する。
   - `RESULT=DEST_CONFLICT` → 手順 7 に戻る。

### 9. 完了を報告する

`references/setup-guide.md`「完了時の案内」の形で、次の 4 点を伝える:

1. Clone したフォルダの場所（`DEST=` の値）
2. Claude Desktop の「Code」タブで、そのフォルダを開く方法
3. フォルダを開いたら、CMS の `/setup-editor` を実行すること
4. セットアップ後は `/cms-help` で使い方を確認できること

あわせて、この Skill で追加したソフト（あれば）を一覧で伝える。

## 守ること

- **インストールは、ソフトごとに明確な承認を得てから、スクリプトの `install-clt` / `install-brew` / `install-gh` だけで行う。** `brew install`・`xcode-select --install`・インストーラーの取得や実行を直接行わない。インストール済みのものを入れ直さない。
- **`sudo` を使わない。管理者パスワードを扱わない。** 管理者の確認は macOS の正式な画面（インストーラー・システムの確認画面）に任せ、編集者本人が入力する。パスワードをチャットに入力するよう求めない。
- **学校・会社の管理制限を回避しない。** 禁止されている・管理者権限がない場合は、理由を伝えて止まる。
- **インターネット上のスクリプトを取得して実行しない。** Homebrew は、スクリプトが公式の配布元から取得し、公式の署名と Apple の確認を検証したインストーラーだけを使う。
- **シェルの設定ファイルは、必要な場合だけ承認を得て `persist-path` で追記する。** 自分で編集しない。
- **認証情報を扱わない。** パスワード・トークン・確認用コードを尋ねない、貼り付けを求めない。`gh auth token` や `gh auth status --show-token` など、トークンを表示するコマンドを実行しない。
  ユーザーが貼り付けてしまった場合は、その値を繰り返さず、無効化（再発行）を勧める。
- **アカウントの切り替え・ログインは、毎回明確な承認を得てから、スクリプトの `switch` / `login` だけで行う。** `gh auth switch` / `gh auth login` を直接実行しない。
- **ログアウトしない。** `gh auth logout` は絶対に実行しない。既存アカウントのログインは常に残す。
- **ブラウザでのログイン・承認は本人が行う。** あなたがブラウザを操作して GitHub にログインしたり承認したりしない。
- **確認用コードを見ない・表示しない。** `pbpaste` などでクリップボードを読まない。
- **既存のファイル・フォルダを削除・上書きしない。** `rm -rf`、`git reset --hard`、`git clean`、`git checkout -- .`、`git stash` などを実行しない。
- **既存のリポジトリを変更しない。** 再利用する場合でも `git pull` / `git fetch` / `git commit` / `git push` をしない。
- **コミット・Push・PR 作成をしない。** CMS 本体のファイルも編集しない。
- **Docker・Astro・プレビュー・記事の作成や公開は扱わない。** それらは Clone 後に CMS 側の `/setup-editor` 以降の Skill が担当する。
- スクリプトの結果と異なる内容（失敗したのに成功したなど）を伝えない。実行できなかった操作を、実行できたと伝えない。
